# P24 — Training under declared settings; absolute risk floors

## Why

A real session collected training data with a declared rule switch on (for example "bypass the
heuristic cancel") and then could not train from it: a trainer that admits only data generated by
the exact policy it trains for compares the base candidate's rendered settings, and a candidate's
settings could not be chosen in `TRAIN_MODEL`. The only route was to rewrite the rule as a patch,
whose text never equals the switch, so the matching data was refused (`DATA_POLICY_MISMATCH`).

Owners also state hard bounds as absolute values (for example "mean PR must stay above 0.001"),
while `RiskLimit` could only bound a metric's worsening relative to the matched baseline.

## Change

- `TrainModelAction.settings`: declared strategy settings, checked against the contract like a
  `BACKTEST` experiment's settings. The trainer receives the base under them, and the trained
  candidate keeps them. The training job key includes them only when given, so earlier training
  jobs keep their keys.
- `RiskLimit.floor`: an absolute worst admissible value (a minimum for metrics to maximize, a
  maximum for metrics to minimize). `max_worsening` is now optional; a limit needs at least one.
  A floor-only limit does not need the baseline's value.

## Evidence

- `tests/test_autonomy.py::test_training_settings_reach_the_trainer_and_the_trained_candidate`
- `tests/test_autonomy.py::test_risk_limit_floor_is_absolute`
- Validation cases for undeclared and out-of-range `TRAIN_MODEL` settings.
- Full suite, ruff and mypy: see the commit.

## Limitations

Synthetic tests only. Whether a private trainer's admission check accepts the settings is that
adapter's responsibility.
